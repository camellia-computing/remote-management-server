# Release policy

Remote Management uses the same App-authored, review-gated stable-release state
machine as the other product repositories, with an additional Web dependency
boundary.

## Exact release inputs

A formal release binds:

- the merged Release PR commit and its successful `main` push `CI / Required`;
- the stable version generated by Release Manager;
- `web-client.lock`;
- exactly one completed, immutable Remote Client release at that locked commit;
- the Web runtime artifact produced by the same Management CI run; and
- the reviewed registry map.

The dependency resolver requires an App-authored Remote Client Release,
lightweight exact tag, completion marker, valid organization
`release-evidence.json`, and one Web ZIP record. The downloaded CI Web runtime
must record `<locked-commit> clean`, contain every required runtime file, and
contain no symlink.

## Publication flow

Release Manager creates and review-gates `release/next`, verifies exact-head CI
and approval, performs a SHA-guarded squash merge, then prepares the draft
Release and lightweight tag. `publish-release.yml` freezes one Linux
amd64/arm64 OCI layout containing the verified Web runtime, scans the exact
layout, generates SBOM/provenance, and records the client release evidence.
Formal image construction does not import or export a mutable GitHub Actions
build cache.

The protected `release` environment is reached only after the frozen candidate
succeeds. GHCR and Docker Hub publication is conditional on the reviewed
`CONTAINER_REGISTRY_MAP`; configured targets receive identical digest bytes,
version/full-commit aliases, and keyless Cosign signatures. Release assets are
checksummed, signed, uploaded and publicly read back before completion.
`latest` is reconciled only to the highest completed stable version and is
never a deployment input.

Manual dispatch is recovery-only for an existing managed tag. It never chooses
new source, version, architecture, or registry values. Any conflicting lock,
client evidence, Web bytes, digest, signer, uploader, tag, Release metadata, or
alias fails closed.

## Required hosted configuration

- Release App client ID, login, and private key;
- protected `release` environment with non-self review;
- complete logical `REMOTE_REPOSITORY_MAP`;
- complete `CONTAINER_REGISTRY_MAP`;
- Docker Hub credentials only when its target is configured.

The App needs only the repository permissions requested by each workflow. It
does not receive Actions or Workflows write access. Service repositories do
not receive desktop/mobile signing keys.

GitHub exposes the complete repository merge-policy fields only to a caller
with push access. The hosted-policy check therefore uses a separate,
repository-scoped App token with short-lived Contents write permission. That
token is not reused for release authorization; the authorization controller
receives a distinct read-only token.
