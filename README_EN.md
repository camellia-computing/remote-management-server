# Camellia Remote Management Server

Production management plane for Camellia Remote: accounts, devices, address books, policy, auditing, and a commit-pinned Web client. Production supports PostgreSQL only; SQLite is restricted to explicit `CAMELLIA_REMOTE_DEBUG=true` development. Online plugin signing remains disabled until the repositories provide a versioned artifact envelope, a real verification consumer, and an approval-backed signing workflow.

The service listens on port 21114 behind a TLS reverse proxy. Keep PostgreSQL and the backend network private. The initial single-region target is 99.9% availability, RPO at most one hour, and RTO at most four hours.

## Development

Use Python 3.14, uv 0.12.0, and PostgreSQL 18. Username identity v1 is pinned to Python 3.14's Unicode 16.0.0 data; other Unicode data versions fail closed. For an isolated SQLite development run:

```bash
uv sync --locked --all-groups
CAMELLIA_REMOTE_DEBUG=true CAMELLIA_REMOTE_SECRET_KEY=dev-only-insecure-secret-key \
  CAMELLIA_REMOTE_DEVICE_VERIFICATION_TOKEN=development-device-token-00000000 \
  uv run python manage.py migrate
uv run ruff format --check .
uv run ruff check .
uv run pytest
```

## Production

Copy `.env.example` to a mode-`0600` secret file and set every required value, especially `CAMELLIA_REMOTE_SECRET_KEY`, the stable lowercase `CAMELLIA_REMOTE_DATA_ENCRYPTION_KEY_ID`, its canonical 32-byte Base64 `CAMELLIA_REMOTE_DATA_ENCRYPTION_KEY`, `CAMELLIA_REMOTE_DATA_ENCRYPTION_V1_KEY_ID`, `CAMELLIA_REMOTE_DEVICE_VERIFICATION_TOKEN`, PostgreSQL connection parameters, explicit public HTTPS origins, WSS rendezvous endpoints with ports, and the canonical 32-byte Base64 `CAMELLIA_REMOTE_RS_PUB_KEY`. A non-Compose process uses either `CAMELLIA_REMOTE_DATABASE_URL` or the complete `HOST/PORT/NAME/USER/PASSWORD` settings, never both. Production Compose instead requires five distinct `BOOTSTRAP/MIGRATION/RUNTIME/BACKUP/PROBE_USER/PASSWORD` pairs; all usernames and passwords must differ, and every password is at least 16 characters. On the first upgrade of an existing volume, the bootstrap pair must name that cluster's current superuser. Keep it as root-only, audited break-glass material: it is passed only to PostgreSQL initialization and the one-shot bootstrap client, never to Management, migration, backup, or probe. Compose uses discrete parameters, so URL-reserved characters in strong passwords need no encoding. Production requires TLS. Invalid booleans, integers, log levels, and time zones stop startup rather than silently falling back. Never place secrets in images, Git, or shell history. Configure all OIDC values together. Unknown OIDC subjects are denied unless pre-bound in Django Admin. Auto-provisioning must be explicitly enabled with at least one exact verified-email domain or JSON claim allowlist; every configured claim is required, and policy-managed identities are rechecked on every login.

Username identity v1 strips surrounding whitespace, applies NFKC, Unicode full casefold, and a second NFKC, then stores the result as a unique UTF-8 binary key. Password login, OIDC allocation, exact account lookup, registration, and login-admission buckets all use that key; PostgreSQL `lower`, `iexact`, and ambient locale no longer define account identity. New Compose databases are fixed to UTF8 with the builtin `C.UTF-8` provider and collation version 1. Migration 0026, process startup, readiness, backup, and restore fail closed on a different schema, canonical value, locale provider, or collation version. Historical collisions are reported with a bounded list of user IDs and canonical digests and are never automatically merged or renamed.

`POST /api/users` returns `409` with machine code `username_conflict` only when the canonical username precheck matches or an isolated user-insert savepoint fails and the same canonical account is then read back. Concurrent creation of one requested Group rolls back only its insert savepoint, locks and reuses the committed Group, and lets distinct users join that one target. A Group that cannot be read back, an M2M failure, or any other unknown integrity error remains a 5xx and rolls back the whole user creation; it is never mislabeled as a username collision.

Before discovery, token exchange, JWKS retrieval, or local provisioning, an OIDC callback claims its pending state as `processing` in a short transaction with a random owner, monotonic generation, and bounded lease; it holds no database lock during external HTTP. Only a worker whose owner/generation still matches and whose lease remains live may commit user/identity provisioning and pending `done` in one transaction. Provider errors and late workers cannot overwrite an active or newer claim, while an expired claim can be reclaimed by incrementing its generation. `CAMELLIA_REMOTE_OIDC_CALLBACK_CLAIM_LEASE_SECONDS` must cover four OIDC HTTP deadlines—discovery, token, JWKS, and an unknown-`kid` rotation refresh—plus 15 seconds of local margin; shorter configurations fail closed at startup.

OIDC discovery and JWKS use external-document contract v1. A response must be at most 1 MiB of BOM-free UTF-8 JSON, with only `application/json` or `application/jwk-set+json` and an optional unique `charset=utf-8`. Duplicate or NFC-equivalent keys, non-finite numbers, integers outside 64 bits, nesting beyond eight levels, more than 64 members in one container, more than 2,048 total nodes, or strings beyond 8 KiB are rejected before JOSE processing. Discovery retains only the configured issuer, allowlisted HTTPS authorization/token/JWKS/userinfo endpoints, and at most 16 unique safe signing algorithms. A JWKS has at most 32 public signature keys with unique 1–128-byte printable ASCII `kid` values and accepts only 2,048–8,192-bit RSA, P-256/384/521 EC, or Ed25519 keys; `alg`, `use`, `key_ops`, and curve must match, while private, unknown, or non-canonical key material is rejected. Bounded X.509 metadata is validated then discarded before JOSE import. Both validated document types share a 16-entry LRU, five-minute fresh TTL, ETag revalidation, and single-flight. Only a transport or HTTP failure may use a validated stale copy for 15 additional minutes; a schema failure never pollutes the cache. An unknown token `kid` forces one JWKS refresh and still fails closed if it remains unmatched.

Gunicorn access logs contain only the method, fixed route pattern, status, byte count, duration, and a server-generated request ID. They never include a raw URL/query, Referer, User-Agent, or client address. Reverse proxies must enforce the same boundary and must not log OIDC code/state values, share tokens, audit/session/device parameters, or recording filenames.

Request admission is mandatory in production; setting `CAMELLIA_REMOTE_RATE_LIMIT_ENABLED=false` stops startup. Each process first applies a bounded monotonic in-memory window to global and source ingress before URL resolution, sessions, or database access. `/health/live` and `/health/ready` bypass only shared database admission and remain subject to this local ingress cap. PostgreSQL then provides atomic fixed windows and short-lived concurrency leases across replicas for global/service, IPv4 `/32` or IPv6 `/64` source, route, bearer credential, actor credential generation, device deployment generation, and declared recording bytes. The tables contain only domain-separated SHA-256 identities and fixed scope/group labels, never raw IPs, tokens, actors, or devices. These hashes are pseudonymous rate keys, not anonymized data.

A rejected request returns 429 with bounded `Retry-After`, `RateLimit-Limit`, and `Cache-Control: no-store`; a shared-admission backend failure returns a stable 503 without database details. The five-minute cleanup timer reclaims expired buckets and crash-left leases, and the configured lease duration must exceed the longest permitted Gunicorn request. `.env.example` documents service, source, credential, recording-byte, concurrency, and local-capacity limits. Application admission does not replace edge/WAF connection, body, bandwidth, or request limits, nor network restriction of health endpoints. When forwarded headers are enabled, the trusted-proxy CIDRs must be complete and the proxy must overwrite client-supplied source headers, or source budgets have no trustworthy boundary.

Every JSON API request accepts only unencoded `application/json` with an optional single `charset=utf-8`, requires one accurate canonical decimal `Content-Length`, and rejects `Transfer-Encoding` and `Content-Encoding`. Before any mutation, the parser applies separate byte budgets to authentication, ordinary control, audit, management-batch, and address-book-bulk routes. It rejects duplicate or Unicode-NFC-equivalent keys, non-finite numbers, oversized number/string/key tokens, nesting beyond 64 levels, more than 10,000 items in one container, or more than 250,000 total nodes. Known syntax errors return bounded JSON 400, byte limits return 413, and wrong media types or encodings return 415. `/api/share` applies the same strict JSON contract to exactly one bounded URL-encoded or multipart `data` field. The TLS edge must bounded-buffer HTTP/1.1 chunked or HTTP/2 DATA, remove `Transfer-Encoding`, and emit an accurate length; if it cannot establish that boundary, it must reject before forwarding to Gunicorn. The JSON budgets in `.env.example` are independent of recording chunks, so increasing a recording chunk never expands login or control-plane input.

User, device, device-group, and strategy management mutations use an exact per-method field allowlist. Unknown or read-only fields, missing required fields, simultaneous `name` and `username` aliases, and a PATCH with no mutable field are rejected with 400 before a database lookup or save. The response carries fixed `field_contract_version=1`, machine code `invalid_request_fields`, and sorted field names, but never echoes field values. A valid PATCH or device assignment saves only explicit fields, and its success audit contains only bounded `changed_fields`. Status and DELETE requests allow only an empty object or an empty body. Strategy status temporarily accepts either a JSON boolean or the exact `{"enabled": BOOLEAN}` object; an object with any extra field is rejected.

Batch strategy assignment, device-group add/remove, user force-logout, individual user/device enable or disable, and device delete requests require a canonical UUID `Idempotency-Key`. In one PostgreSQL transaction, Management persists an operation receipt and serializes these low-frequency control mutations with a transaction-scoped advisory lock. Batch operations lock and verify their complete target set before mutation; status and delete operations lock the authority row and commit its state or deletion together with applicable token, proof-challenge, and recovery-approval revocation. User disable advances the credential generation and deletes that user's bearers. Device disable advances the deployment generation and deletes that device's bearers, proof challenges, and unconsumed recovery approvals, so re-enabling it cannot resurrect a recording upload, audit session, proof challenge, or recovery approval authorized by the older generation. Duplicates, missing targets, exhausted generations, invalid membership, racing deletes, and injected database failures therefore produce either the complete old state or the complete new state. A response receipt contains `management_operation_receipt_version`, the operation ID and monotonic generation, canonical request/result digests, and exact `requested`/`applied` counts; single-target receipts retain only the target database identifier, resulting status, and revocation count rather than copying profile notes, email, host metadata, or IP addresses into the receipt table. Reusing the same ID for the same request after response loss returns the original receipt even after a device row was deleted; binding it to another actor, operation, or target returns 409. An administrator cannot disable or delete the device carrying the current bearer, because doing so would destroy the authority required to replay a lost response; use a different active administrator device for that operation. The batch CLI prints the ID before sending and accepts `--operation-id`; every other caller must likewise persist the ID before sending and verify the receipt before reporting success. The cleanup timer deletes expired receipts in bounded batches according to `CAMELLIA_REMOTE_MANAGEMENT_OPERATION_RETENTION_DAYS`; an ID older than that window must not be treated as a safe idempotent retry.

Recording and audit retention have a second, persistent authority beyond the resetting request windows. A transactionally locked usage ledger applies device, owner, and global limits to active uploads, retained files, committed bytes, connections, and events. A quota rejection is a 507 with bounded `Retry-After`; the Client retains its sidecar and waits rather than retrying each frame. Readiness and every authenticated recording mutation verify that the recording root is still a real writable directory, is a dedicated mount in production, and retains the configured byte and inode reserve before request-body materialization. The bounded cleanup timer converts stale recording partials through recoverable tombstones, removes expired finalized bytes, marks audit sessions whose database-time lease expired as `expired/telemetry_lost`, and removes terminal audit sessions after retention. An expired session deliberately retains `conn_end=NULL` rather than forging a normal disconnect. Device deletion clears only live authority while keeping storage namespace and quota snapshots until cleanup. Operators can place or release an explicit hold with `set_ingestion_hold recording|audit UUID --actor ADMIN --reason TEXT --hold|--release`; Admin pages cannot directly rewrite retained evidence.

Every application-owned automatic primary key and PostgreSQL sequence is a signed 64-bit value. After retention, the five-minute cleanup unit runs `check_sequence_capacity --fail-level critical`. The command retains one fixed-size previous-sample row per current sequence and writes schema-v1 JSON to the journal with last/max/remaining values, consumed parts per million, daily growth, and estimated days to exhaustion. Warning and critical thresholds default to 80% and 95% and can be tightened with `CAMELLIA_REMOTE_SEQUENCE_CAPACITY_WARNING_PERCENT` and `CAMELLIA_REMOTE_SEQUENCE_CAPACITY_CRITICAL_PERCENT`; a critical result fails the unit and must alert operations. Operators can run `python manage.py check_sequence_capacity --fail-level none|warning|critical` for diagnosis, but must never reset, wrap, or reuse a sequence. A 64-bit range only extends the exhaustion horizon: it does not replace ingestion rate limits, persistent quotas, partitioning, or retention, and growth rate, index/disk capacity, and cleanup lag still require monitoring.

Current writes for address-book, device, pending-OIDC, and recording data-key secrets use key-ID-bearing `secretbox:v3` context-bound envelopes. Each encrypted field derives a distinct SecretBox subkey from the master key and a canonical context through HMAC-SHA256. That context fixes the schema, model, field, a database-unique and immutable non-reusable `secret_context` UUID, and the applicable profile, RID, owner, deployment generation, upload, and object authority. Recreating a row with the same business RID generates a new UUID, so old ciphertext cannot be reassigned. `secretbox:v1` and unbound `secretbox:v2` remain migration/rotation readers only; the key-inventory canary intentionally stays on v2 because it contains no business secret. Raw SQL, bulk update, import, restore, and migration code must never copy an envelope between fields or rows. A legitimate copy must decrypt, reauthorize against current authority, assign plaintext to the target model instance, and save to produce a fresh target-context envelope. A database writer without the data key therefore cannot substitute credentials by transplanting valid ciphertext, and any envelope or context mismatch fails before plaintext is returned. A shared profile's default password lives in an explicit encrypted field rather than generic `info` JSON. Profile lists never load or return it; the Client requests it only through a target-RID-bound, authenticated, access-scoped runtime API. Django admin treats credentials as write-only values, and CSV/Excel exports omit them.

Django logical fixtures are not a credential-recovery format. The project shadows `dumpdata` and refuses any effective model selection containing an `EncryptedTextField` before a database query or `--output` file creation; explicitly excluding every secret model still permits ordinary-model exports. The field itself rejects programmatic JSON, JSONL, XML, and optional YAML serializers, so directly calling Django's serializer cannot bypass the command guard. There is no `--include-secrets`, warning-only, or plaintext-stdout mode. Credential and row-context recovery uses only the authenticated encrypted physical backup set, avoiding fixture disclosure, raw-envelope double encryption, and cross-row context misbinding.

The five browser address-book exports use the `address-book-export-v1` contract. `format` defaults to `csv` only when it is entirely absent; explicit values are case-sensitive and limited to `csv`, `xls`, and `xlsx`. `xls` remains a declared alias for legacy callers and produces an OOXML `.xlsx` artifact, while the current UI sends `xlsx`. The single-book export defaults `kind` to `peers` only when absent and otherwise accepts only `peers` or `tags`. Empty, duplicate, case-variant, unknown, or oversized values receive a bounded JSON 400 with machine code `invalid_export_parameter` and the supported values before any data query or artifact build; the raw input is never reflected. Successful responses declare the actual schema through `X-Camellia-Export-Schema`, `X-Camellia-Export-Format`, and, when applicable, `X-Camellia-Export-Kind`. Callers must verify those headers together with Content-Type, filename extension, and CSV/ZIP magic instead of assuming the requested query value describes the artifact.

User, device, device-group, peer-inventory, and the three address-book lists share `pagination-contract-v1`. `current` and `pageSize` default to `1` and `100` only when entirely absent. An explicit value must be a single unsigned positive ASCII decimal without leading zeroes; empty or duplicate values, Unicode digits, and all other non-canonical forms receive `400 invalid_pagination`. `pageSize` is at most 500 and numbered pages may use a database OFFSET of at most 10,000; an over-budget request returns a typed error with the contract version, field, and limits before the list data source is queried. A syntactically valid page beyond the actual result set consistently returns 200 with empty `data`, and every successful paginated response includes the contract version, `current`, and `pageSize`. After the first `/api/peers` response, consumers should follow `nextCursor`: a valid signed cursor is authoritative for position and uses database offset zero, while `current` remains strictly validated response metadata. Consumers of other lists must narrow an exact filter before the next page would exceed the offset window; they must not traverse without a bound or reinterpret a 400 as an empty page.

The control-plane user, device, and device-group lists use `control-filter-contract-v1`. A value without `%` is an exact match, `term%` is a case-insensitive prefix match, and `%term%` is a substring match whose term must contain at least three characters. Device `id` (RID) is exact-only; device hostname/system username/device group, owner username/Django Group, user username/Group, and device-group name accept all three modes. A duplicate parameter, any other wildcard placement, an empty wildcard, an undersized term, or a value over 128 characters/256 UTF-8 bytes receives a typed `400 invalid_control_filter` before the database is queried. PostgreSQL reuses the existing RID and username unique B-trees and adds B-tree or `pg_trgm` expression GIN indexes only for the measured hostname/system-username, device-group name, and Django Group name paths. Callers must rate-limit and bound substring searches and prefer exact or prefix filters; indexes are not a substitute for selectivity and write-amplification measurements.

Device API and Web pages use an explicit narrow inventory projection. Administrators query global devices; regular users combine only their devices with peers from their exact `personal-<owner-id>` profile, and every internal row carries its `source/owner/rid` identity. Permission filtering, stable ordering, and slicing happen in the database before Python objects are built. `/api/peers` keeps numbered-page parameters and also returns an hourly signed `nextCursor` bound to the viewer, authority scope, and status filter; new consumers should use that cursor to avoid duplicate pages during concurrent inserts or deletes. The home page uses separate aggregates and a top-six query. `DeviceInfo-v1.xlsx` reads only its versioned allowlist and is produced through a database iterator, write-only workbook, bounded memory spool, and `FileResponse`. The export is rejected when its configured row, compressed-byte, or generation-deadline budget is exceeded; increasing worker memory is not a substitute for those limits.

Address-book ACL audits commit in the same transaction as the corresponding authorization mutation. Each audit row retains immutable profile GUID, name, and owner snapshots. Deleting a profile first writes a tombstone and then nulls only the live-object reference, so API, Web, Admin, and owner-cascade deletion cannot erase prior ACL history. Django Admin permits viewing these rows but not adding, changing, or deleting them.

Connection auditing accepts only `version=3`; a v2 Client receives 426 and must be upgraded with Management. A host creates a `starting` connection with a one-use UUIDv4 event, after which Management issues an unguessable `audit_session_id` bound to the host device, owner, and deployment generation. The state moves to `active` only after the host fixes the authenticated controller identity. The Client refreshes a default 90-second database-time lease every 20 seconds with a monotonic heartbeat revision; each response binds the acknowledged event, event/state/heartbeat revisions, state, and remaining lease. A stale heartbeat, controller lookup, or event can never revive a terminal row. A normal active close becomes `closed`, an end before authorization becomes `aborted`, and missing close telemetry becomes `expired/telemetry_lost` without filling `conn_end`. The controller can claim the capability only while the host lease is unexpired and both participants are proven; even a replay of a previously successful bind receives 409 after close. Critical facts transition only from unset to fixed and become permanently frozen at a terminal state. Every note is an append-only event retaining the previous and new text, actor, and monotonic sequence. File and Alarm rows are accepted only after both host and controller are bound, both device generations remain current, and the connection remains active. Each row has real foreign keys to the same Connection and append-only event. An event ID is idempotent only when session, kind, actor, device, and complete payload all match; collisions, stale generations, owner changes, and cross-session replays fail closed. Deleting a device or user invalidates its live authority references while retaining snapshots of the device PK, RID, UUID, owner, generation, and every event actor ID. Connection, Event, File, and Alarm records are read-only in Django Admin; corrections require a separate traceable event rather than historical mutation.

File and Alarm evidence additionally requires `receipt_version=1` and a positive reporter sequence. Management stores a SHA-256 digest over the canonical normalized payload plus the session, actor, reporter device PK/generation, event ID, and reporter sequence, and stores the exact acknowledgement in the same transaction. The database uniquely binds each reporter sequence within a session. An identical replay returns that immutable acknowledgement even after later events or close; an event-ID or reporter-sequence collision with different content returns 409 and creates no child row.

Device identity uses one-use `camellia-device-proof-v1` challenges. Password and OIDC login for an enrolled device require a signature from its current Ed25519 device key; first deployment is signed by the new key; proactive key rotation requires old and new keys to sign the same challenge. If the old key is lost, an administrator must approve the exact replacement public key through `POST /api/devices/<device-id>/approve-recovery`. Approval expires after ten minutes, is consumed once, increments the deployment generation, and immediately revokes the old bearer. A Client must validate every canonical message field before signing and must never treat a Management response as an arbitrary-message signing request.

A successful device heartbeat returns a 60-second `device_lease` bound to the rid, UUID, and deployment generation; clients renew it on the existing 15-second idle or 3-second active cadence. After device disable/deletion, owner invalidation, or unified credential revocation, heartbeat with the old bearer returns an explicit `revoked` state bound to that rid and UUID. Client must immediately reject new incoming connections and close existing direct, relay, file, and terminal sessions. Network or Management failure is not treated as an explicit revocation, but the Client still fails closed when its last valid lease expires.

Identity Server supplies a random 32-byte nonce to every `POST /api/devices/verify-deployment` request. Management returns a 30-second `camellia-deployment-assertion-v1` JSON assertion, HMAC-SHA256-signed with the shared verification key and bound to the rid, UUID, public-key hash, deployment generation, and nonce. The former static 204 contract is removed. Management, Client, and Server therefore require a coordinated upgrade, and Server permits replacement of persisted identity only at a higher generation.

For rotation, configure the new ID/key as primary, retain the old key as an `old-id:Base64` entry in `CAMELLIA_REMOTE_DATA_ENCRYPTION_LEGACY_KEYS`, and keep `CAMELLIA_REMOTE_DATA_ENCRYPTION_V1_KEY_ID` on the key that produced legacy v1 rows. Run `python manage.py rotate_data_encryption --dry-run`, then run bounded batches; `--max-batches` supports deliberate interruption and resume. For every encrypted column, the command locks and reads the complete declared row context, authenticates legacy v1/v2 or current v3, and rewrites to primary-key v3 without falling back to an unbound envelope. Recording data-key rotation also updates `data_key_kek_id` without rewriting the large volume ciphertext. After all batches, run the command once without `--max-batches` to authenticate every primary v3 envelope against its full row context. Use `--retire-key-id OLD_ID` only after that full validation, an isolated restore validates the same contexts, readiness passes, and retained backup inventory no longer requires the key; retirement counts v1, v2, and v3 references. When deleting the old secret, also move `CAMELLIA_REMOTE_DATA_ENCRYPTION_V1_KEY_ID` to a key that remains configured.

Recording ingestion accepts only upload protocol `version=2`; legacy `new/part/tail/remove` requests receive HTTP 426, so Client and Management must be upgraded together. The Client persists a random create ID before the request and Management issues an upload ID bound to the device owner and deployment generation. Every chunk carries its offset, base revision, random chunk ID, length, and SHA-256 digest. Management acknowledges a new authoritative offset/revision only after the staging file is synced and the database receipt commits; an identical chunk can therefore be replayed after a lost response, and status must match that exact receipt rather than infer success from an advanced offset alone. Partial writes are truncated to the last committed offset. Finalize verifies the complete size and digest, publishes by an atomic same-filesystem rename followed by syncing both source and destination directories, and permanently rejects later append or abort operations. Active `.uploads/*.part` files are never completed recordings. After restart, the Client recovers ambiguous chunk/finalize state from two checksummed sidecar slots protected by Unix mode 0600 or the Windows recording-directory ACL, and performs an idempotent abort when it cannot prove the local recorder closed normally. A later storage-governance change must bound retention and cleanup for upload rows, chunk receipts, and expired staging files; operators must not delete only one side of this state or treat staging data as evidence.

Every `/api/record` POST requires exactly one valid decimal and accurate `Content-Length`, including an explicit `Content-Length: 0` for empty create, status, finalize, and abort bodies. Before storage admission or any filesystem/database mutation, Management rejects Transfer-Encoding/chunked with 400, a missing or empty length with 411, an invalid or ambiguous length with 400, and a length above the configured chunk limit with 413. The query length must still exactly match both the transport length and bytes actually read. The production TLS edge must buffer HTTP/1.1 chunked or HTTP/2 DATA within the hard `CAMELLIA_REMOTE_RECORD_UPLOAD_MAX_CHUNK_BYTES` limit, remove Transfer-Encoding, and emit exactly one accurate Content-Length; if it cannot establish that boundary, it must reject the request before proxying instead of streaming it to Gunicorn. Gunicorn must remain reachable only from the trusted internal edge. Its duplicate-CL and CL+TE parser rejection is defense in depth, not a replacement for the edge contract. The current Client sends fixed `Bytes`/`Vec` bodies, for which reqwest emits an accurate Content-Length, so no legacy transport mode is retained.

Install `docker-compose.yaml`, `deploy/bootstrap-postgres-roles.sh`, `deploy/run-compose-operation.sh`, `deploy/backup-postgres.sh`, `deploy/run-cleanup.sh`, `deploy/restore-postgres.sh`, `deploy/management-maintenance-guard.sh`, `deploy/management-maintenance.sh`, `deploy/start-management-stack.sh`, `deploy/stop-management-stack.sh`, `deploy/shutdown-budget.sh`, `scripts/backup_envelope.py`, and `deploy/systemd/*` as documented in the Chinese README. Pin `CAMELLIA_REMOTE_MANAGEMENT_IMAGE` to a published `sha256` digest. The systemd stack has no online reload entry point. `CAMELLIA_REMOTE_GUNICORN_GRACEFUL_TIMEOUT_SECONDS` is the only tunable application drain window; `deploy/shutdown-budget.sh` derives Docker grace as `G+15s` and validates the fixed 660-second systemd outer budget. Compose `stop_grace_period`, the controller's `docker compose stop`, and systemd `ExecStop` all use that validated result, and any drift fails closed before Gunicorn binds or Docker mutates the stack. Every start uses a single-flight controller that stops the old Management container, starts PostgreSQL without waiting for the not-yet-created probe role, and uses the bootstrap superuser to converge role flags, memberships, database/schema/object ownership, current ACLs, and migration-owner default ACLs in one advisory-locked transaction. It then requires an authenticated probe and runs `migrate_with_lease` only as the migration owner. That command holds the fixed `CAMELLIA` PostgreSQL session advisory lock around the complete Django plan, reports the release revision, actor, operation ID, holder backend, and a five-second wait heartbeat, and exits 75 after the bounded `CAMELLIA_REMOTE_MIGRATION_LOCK_TIMEOUT_SECONDS` deadline. PostgreSQL releases the lease if the holder connection disappears; a follower constructs a fresh executor and plan only after it acquires the lease. The controller converges and probes again, and starts Management with only the runtime DML credential and `restart: no`. Runtime never owns the database, schema, or tables and remains `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`; its access to `django_migrations` is read-only so it cannot forge the schema ledger. `check_release_schema` compares the exact migration set and leaves plus critical table, column, type, validated-constraint, and ready-index capabilities against the versioned release manifest before Gunicorn binds. `/health/ready` continuously applies the same fail-closed contract, so missing, extra, forked, or physically drifted schema is not ready. Backup is read-only and probe has no public-schema or business-table access. Deployment and maintenance enter/leave share a protected deployment lock, and an active maintenance lease rejects startup before Docker is invoked. Docker Engine or a container restart therefore cannot bring Management up without the migration and role gate. Rotate a limited-role password by changing the protected environment file and running the controller while offline; convergence invalidates the old password. Application failure must alert and enter this controlled start path instead of using an Engine restart policy.

Every PostgreSQL application session starts with non-zero statement, lock, and idle-in-transaction timeouts. The runtime defaults are 45/5/15 seconds within a 50-second monotonic database operation budget. The outer HTTP request has a default 65-second monotonic budget and remains below the 75-second Gunicorn worker-failure boundary. Gunicorn explicitly uses `gthread`; its heartbeat timeout is only a last-resort process failure guard, not a per-request SLO. Python does not force-kill an arbitrary request thread: database, request-body, recording-file, and OIDC downstream operations must consume the remaining request budget. A 10-second idle, five-second interval, three-probe TCP keepalive and a 30-second `tcp_user_timeout` also fail half-open links before the operation boundary. Migration, cleanup, and backup use separate longer profiles. If elapsed non-database work leaves less time, the next transaction/session setting is only tightened, never extended. Configuration requires the statement, idle, TCP, and keepalive detection boundaries to remain shorter than the operation budget, and the request budget must cover the four OIDC discovery/token/JWKS/key-rotation HTTP deadlines. SQLSTATE 57014, 55P03, and 25P03 are classified without localized message matching, and a timed-out connection is discarded. An HTTP budget timeout returns 504 with `retryable=true` and `result=unknown`; a database timeout returns 503 with `retryable=false` and `result=unknown`. Callers must read authoritative state or an idempotent receipt before retrying a mutation.

Compose gives Management, one-shot migration, PostgreSQL, and each database client independent finite CPU, memory reservation/max, PID, nofile/nproc, I/O-weight, and OOM-priority budgets. The default envelope is approximately PostgreSQL + Management at 3 CPUs/3 GiB steady state; migration runs only after the controller stops Management with a separate 2 CPU/1 GiB profile, and backup uses the existing 1 CPU/512 MiB profile. PostgreSQL `max_connections=128`, `shared_buffers=512MB`, `work_mem=4MB`, and `maintenance_work_mem=128MB` must be calibrated with Gunicorn/admission concurrency against real device, recording, and export loads; they are not measurements for 1/100/10k scale. Production Management/migrate containers require finite cgroup v2 `memory.max`, `pids.max`, and `cpu.max` values above the safety floor before startup. At a limit, the edge and supervised controller must shed admission and back off; do not rely on a host OOM victim chosen at random. Any budget change must retain capacity evidence, PSI/cgroup events, p95/p99, and recovery time rather than merely increasing a limit to hide overload.

Committed migration history is an immutable Python API. `api/migration_compatibility_manifest.json` locks every runtime path used by historical files—`EncryptedTextField`, `MyUserManager`, `share_link_expiry`, and `AuditSearchDocument`—together with their deconstruct semantics. `api.test_migration_compatibility` scans every migration's explicit runtime imports and fails closed when a path is added, removed, renamed, or no longer importable. If a business implementation moves, retain an equivalent shim at the old path and add a new migration; never rewrite `0001` or another committed historical file.

Bootstrap, migration, cleanup, backup, and restore database actions run as named one-shot containers labeled with their operation IDs. Cancellation or an inner deadline sends TERM, applies a bounded kill/remove fallback, and confirms that exact remote container is gone. Backup has a 45-minute monotonic budget, and `pg_dump` waits at most 30 seconds for a schema lock. PostgreSQL plaintext is never written to the backup directory. Each run uses a non-reusable random 128-bit backup ID and a private 0700 work directory. All three final paths are published with exclusive hard links; a collision fails immediately, and cleanup removes only paths that this run proved it published, never a pre-existing recovery point. After the database and recording ciphertexts reach their final paths, the protected age identity authenticates and decrypts them again: `pg_restore --file=/dev/null` must decompress every custom-archive data block, and the recording verifier must parse every object and digest. Only then is the third `backup-set-<UTC timestamp>-<random backup-id>.manifest.age` completion marker published. It binds a positive monotonic generation, the previous backup ID, exact ciphertext sizes/SHA-256 digests, deployment/database, PostgreSQL major, source revision, pinned image digest, release-schema generation, key ID, and recording epoch. A final read verifies all three paths before the recording checkpoint and generation-bearing `latest-verified.json` advance.

Database export and full-read verification always run in the digest-pinned PostgreSQL 18 `database-backup` one-shot client, never inside the live PostgreSQL container. Its Docker cgroup is hard-limited to one CPU, 512 MiB of memory, and 64 PIDs, with lower CPU/block-I/O weight and a higher OOM score. The systemd CPU, memory, and task limits cover only host-side age, packing, and Docker control processes and are not presented as a limit on `pg_dump`. Custom archives default to `CAMELLIA_REMOTE_BACKUP_COMPRESSION=zstd:3`; only `none`, `gzip:1..6`, and `zstd:1..9` are accepted. Before changing it, benchmark representative dump wall time/CPU/RSS/bytes, full-restore time, and serving p95/p99 together. Never restore gzip levels 7–9 for a marginal size reduction. An OOM, deadline, or RPO alert calls for a larger backup window, a controlled replica, or a measured compression/data adjustment, not removal of the cgroup boundary.

The identity secret remains only in a root/administrator-owned 0400/0600 file; the environment file carries its absolute path, and the runtime container, image, and artifacts never receive it. Copy and delete the database, recordings, and set manifest as one generation. Before every run, all matching manifests must authenticate into one contiguous, unique predecessor chain for the current deployment/database; a missing, duplicate, forked, or invalid set is preserved and fails closed instead of resetting generation. Retention protects the newest configured generations by that authenticated order, uses monotonicized manifest completion time only as an additional age condition, and never reads mtime. A rollback, a current clock before the chain head, or a forward step beyond `CAMELLIA_REMOTE_BACKUP_MAX_CLOCK_STEP_SECONDS` emits `retention-skipped:*` and deletes nothing. Normal runs remove at most `CAMELLIA_REMOTE_BACKUP_RETENTION_MAXIMUM_DELETIONS` oldest sets. Kernel `flock` remains the single-flight authority. Bounded holder metadata records run ID, start, phase, and heartbeat: a live collision reports `skipped:active-run` with exit 75, a stale heartbeat alerts as failure, and orphan metadata is explicitly recovered. Backup and cleanup units have no start-propagating dependency on the stack and may reach Docker only through its root-equivalent local Unix socket.

The Compose default uses `sslmode=disable` only for PostgreSQL on its non-routable, same-host `backend` bridge. External or cross-host databases are required to use `verify-full`, a trusted CA, and a hostname covered by the certificate. Private CA, client certificate, and client key paths can be supplied with `CAMELLIA_REMOTE_DATABASE_SSLROOTCERT`, `CAMELLIA_REMOTE_DATABASE_SSLCERT`, and `CAMELLIA_REMOTE_DATABASE_SSLKEY`; the client certificate and key must be configured together.

Store encrypted backup sets on independent monitored storage, copy them off-site daily, and run scheduled restore drills. Enter the maintenance lease and prepare an isolated empty PostgreSQL target plus an empty recording volume. Supply the exact manifest release/image context, protected identity path, an audited target ID, an absolute evidence directory, and the per-run confirmation `restore:<backup-id>:<target-id>`; the script rejects a non-empty database or volume. It authenticates all three files and ciphertext digests before mutation, performs the complete single-transaction restore, leased migration, ACL convergence, release-schema and username checks, a data-encryption dry-run over every context/key canary, recording installation, and the final probe. Only complete success creates a non-overwriting age-encrypted restore receipt and advances `latest-restore-verified.json` with completion time and RTO. Failures never advance restore freshness. Stop the isolated target before leaving maintenance, then manually start and verify the stack before restoring traffic or timers. Rotate backup recipients independently from application data-encryption keys, retaining old identities until every retained generation is migrated, restore-verified, or expired.

`web-client.lock` identifies the only Web source accepted by CI. A formal
Management release also requires that exact commit to be a completed immutable
Remote Client release with valid evidence, then reuses the Web artifact from
the exact successful Management push CI. Release Manager creates a reviewed
version PR and exact tag. The workflow freezes and scans one multi-architecture
OCI layout before protected approval, publishes the identical digest only to
configured GHCR/Docker Hub targets, signs and publicly reads back all evidence,
